Privacy and control are features — not footnotes.

Stewart is built on a simple principle: intelligence shouldn't require surrendering your data or your authority. This page explains how permissions, local-first processing, approval gates, and auditability work together to create trust.

The Stewart privacy model

Many "AI assistants" are only powerful because they centralize everything in someone else's cloud. That model is fine for casual usage, but it becomes unacceptable when your workloads include customer data, financial records, internal contracts, or regulated communications. Stewart is designed to run inside your environment with configurable boundaries. In practice, that means three things: (1) explicit permissions instead of implied access, (2) local-first options where raw data can stay local, and (3) auditable execution so actions are traceable.

Explicit permissions

Stewart is not a ghost account with full access. Permissions define what it can read, what it can draft, and what it can execute. You can start with read-only analysis and expand over time.

Local-first options

Sensitive workloads can be processed locally so raw inputs don't have to leave your machine or cluster. You decide the tradeoffs: speed, cost, and privacy — intentionally.

Auditability

When Stewart acts, it logs what it accessed, what it generated, what it changed, and what required approval. Trust scales through logs, not vibes.

Permission boundaries that make sense

"Can you access my email?" is the wrong question. The right question is: what scope, for what purpose, with what approval? Stewart supports boundaries that map to how real operators think about risk.

Access scope

Scope defines which sources are allowed: folders, drives, exports, systems, and accounts. It can be as narrow as a single directory (/calls/Q1_2026) or as broad as an operational data lake — but it's always explicit.

  • Data scope: files, folders, databases, exports.
  • System scope: which web dashboards/apps Stewart can touch.
  • Time scope: limit to a date range or "new since last run."

Action scope

Scope also defines what Stewart is allowed to do. Read-only analysis is one category. Drafting documents is another. Execution is the most sensitive category and should be gated by approvals and safe defaults.

  • Read: summarize, extract, measure, compare.
  • Draft: reports, emails, memos, checklists.
  • Execute: download/export, upload, update records, submit forms.

Recommended onboarding path: Start with read-only analysis → add drafts with review → enable execution with approvals → then automate proven workflows. That progression delivers value immediately without forcing a leap of faith.

Approval gates and "dry runs"

If you want Stewart to be powerful and safe, approvals are your friend. Stewart can operate in a propose/preview/execute loop: it proposes actions, shows you exactly what it plans to do, and only executes after confirmation. For new workflows, you can run in "dry run" mode where outputs are generated but no external changes occur.

Propose

Stewart generates a plan: which sources, which steps, which outputs. This makes execution explainable and gives operators a moment to correct assumptions before anything happens.

Preview

Before an action, Stewart shows the exact change: the email draft, the updated record, the generated CSV, the form fields to be submitted. This prevents "silent errors" and builds confidence quickly.

Execute

Execution happens within the defined scope and produces an audit trail. If anything fails, the log explains what step failed and why, so the workflow can be improved instead of abandoned.

Retention and data handling (practical rules)

Privacy isn't just "where the model runs." It's also what data is stored, for how long, and in what form. Stewart should default toward storing the minimum needed to make workflows repeatable: structured outputs and logs, not raw sensitive inputs.

Store structured outputs

Summaries, scorecards, metrics tables, and action queues are useful and reviewable. They're also smaller and safer than raw audio or full document dumps. Storing structured outputs enables trend tracking without expanding risk.

  • Weekly executive briefs
  • Rep coaching scorecards
  • Objection frequency tables
  • Anomaly flags + links to source references

Minimize raw retention

Keep raw inputs where they already live (your storage) and avoid duplicating them inside the AI system. When the workflow needs source grounding, store references (file path + timestamp) rather than copying the whole asset.

  • Reference: filename + time markers
  • Hashing/versioning for repeatability
  • Configurable retention windows

FAQ

Can Stewart work without sending data to third parties?

Yes — Stewart supports local-first processing options so sensitive workflows can remain inside your environment. If you choose to use external services for certain tasks, that's a deliberate configuration choice, not the default.

How do you prevent "unexpected actions"?

By design: explicit scopes, approval gates, and audit trails. New workflows can run in dry-run mode. Action agents should never be enabled globally; they're enabled per workflow with clear permissions.

What does an audit trail actually include?

At minimum: which sources were accessed, which workflow version ran, what outputs were created, what actions were attempted, what approvals were recorded, and what errors occurred. This is what makes reliability improvable.
