Architecture that's built to run — not just demo.

Stewart is designed like infrastructure: stable layers, explicit boundaries, repeatable workflows, and auditable execution. This page explains how the system is organized so operators can trust it with real work — not just prompts.

The three-layer model

Stewart is deliberately separated into Analysis, Execution, and Control layers. Most AI products collapse these into one blob, which is why they feel powerful in a demo and unreliable in production. Stewart treats them as distinct concerns: analysis converts messy inputs into structured outputs; execution turns structured outputs into actions; control defines what's allowed, what's reviewed, and what's logged.

1) Analysis layer

Ingestion + extraction. Stewart processes audio, documents, exports, and notes to produce decision-ready artifacts: summaries, trend reports, tables, action queues, and "what changed since last run" diffs. The goal is operational usefulness, not academic perfection.

2) Execution layer

Workflow + action. Stewart can draft emails, create reports, move data between systems, and operate inside web dashboards when no API exists — but only within explicit scopes and approval gates defined by the operator.

3) Control layer

Permissions, boundaries, and audit. This layer defines access (read vs write), required approvals, data retention, and the log of "what Stewart attempted / created / changed." Control is what makes scaling trust possible.

Deployment patterns

Stewart supports multiple deployment patterns depending on your workloads. The key principle: don't let a long-running analysis job compete with your interactive experience or your execution safety. Separation keeps the system stable even under heavy use.

Single-node (starter)

One machine runs analysis + interactive tasks, with execution actions gated behind confirmations. This works well for early-stage usage, smaller datasets, and operators who want value fast. As you scale, you split workloads without changing how users interact with Stewart.

  • Best for: personal ops, small teams, early pilots.
  • Strength: simple setup and maintenance.
  • Constraint: heavy batch jobs can impact responsiveness.

Multi-node (operator-grade)

Dedicated nodes for batch analysis (e.g., call archives) while a separate node handles interactive orchestration. Execution can run in a sandboxed environment or VM to isolate risk. This is the "built to run all week" configuration.

  • Best for: high-volume audio/doc processing, enterprise workflows.
  • Strength: stable performance under load.
  • Constraint: requires basic ops discipline (monitoring, storage rules).

Design rule: keep interactive orchestration "light" and move heavy lifting into batch jobs. That's how Stewart stays fast while still processing large datasets like hard drives full of call recordings.

Agents, scopes, and safety boundaries

Stewart works best when capabilities are separated by intent. "Read-only analysis" is fundamentally different from "take an action in a live system." The architecture reflects that difference so you can increase capability over time without losing control.

Read-only agents

Ingest and summarize. These agents can access defined sources and generate outputs, but cannot modify systems. Ideal for early value: digest call archives, summarize documents, generate weekly briefs, and surface anomalies safely.

Draft agents

Produce work products: emails, reports, structured plans, checklists, and scripts. Draft agents write, but their output is reviewed by humans before it becomes action. This is where speed increases without risking unintended changes.

Action agents (gated)

Execute within explicit scopes. Examples: download a statement, pull a report, reconcile a CSV, update a record, file a ticket. Actions can require step-by-step approval, and should always generate an audit trail.

Scopes are explicit

Stewart should never be "all access." Scopes define what data sources are allowed (/calls/2026_Q1), what systems are allowed (e.g., CRM, billing portal), and what actions are allowed (read-only, export-only, or write-enabled).

  • Source scope: folders, drives, exports, databases.
  • System scope: which websites/apps can be accessed.
  • Action scope: read, draft, execute, with approvals.

Approvals scale trust

Approval gates are not a limitation — they're a growth path. Operators can start conservative (Stewart proposes actions) and move toward automation as confidence builds. The architecture supports both without changing the user experience.

  • Propose → approve → execute.
  • Preview before writing/changing data.
  • "Dry run" mode for new workflows.

Repeatability, not one-off brilliance

Real operations require repeatability. Stewart is built to run the same workflow next week and produce comparable outputs: the same metrics, the same sections, the same formatting, and the same definitions. That consistency is what lets teams compare results over time and trust the system in decision-making.

Structured outputs

Workflows define outputs as artifacts: scorecards, summary memos, CSV tables, dashboards, and task queues. Structured outputs are easier to review, version, and reuse than chat transcripts.

Versioned workflows

When you improve a workflow, you version it. That prevents silent behavior changes. Operators should always know which workflow produced a report and what assumptions it used.

Auditability

When Stewart acts, it logs: what it accessed, what it generated, what it changed, and what required approval. That log is how you detect mistakes early and continuously improve reliability.
